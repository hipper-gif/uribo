## Context（背景・なぜ決める必要があるか）

ADR-0002 のCLIで 2026年度4〜7月を再取込したところ、TKC親科目に複数のうりぼーitemが混ざるケースで2種類の取りこぼしが出た。

1. **商店街費が家賃に吸われていた。** 寝屋川の固定費は毎月3本（家賃121,000＋水道3,000＝ヒガシウチ宛124,000／守口家賃100,000／大利商店街振興組合11,800）だが、TKC 6215 地代家賃には**この3本が全部「固定費」の一言で計上され取引先名も空欄**。既存ルールは 6215→`rent` 一択だったため商店街費11,800が rent に吸収され、`shopping_street` が毎月0になっていた（2026/06・07）。逆に shopping_street を手入力していた月（2026/04・05）は rent と**二重計上**（11,800円ぶん経費過大）だった。
2. **分類先が変わった細目に旧値が残り二重計上になる。** 2026/04 の 6113 広告宣伝費は、旧データが `hpb 132,000 ＋ advertising 17,670` だったが、取引先=リクルートなので分類器は全額を hpb 149,670 に寄せる。分類器経路は「分類された code の draft しか作らない」ため、触られない `advertising 17,670` がそのまま残り、合計167,340＝**17,670の二重計上**になる寸前だった。

さらに、TKC側の仕訳そのものが間違っている月があった（2026/05は美容の家賃部門が逆＝011に100,000・012に124,000）。この月をそのまま取り込むとうりぼーの正しい値が壊れる。

## Decision（確定した主要決定＝1決定1行）

| # | 決定 | 理由（1行） |
|---|------|------|
| D19 | **6215 地代家賃を `rent` / `shopping_street` に分離し、判定は金額定数 `SHOPPING_STREET_FEE`(11,800)で行う** | 取引先名も摘要も無い（空欄＋「固定費」）ので金額でしか区別できない。`WADA_FIXED_FEE` と同じ発想。額が変わったら定数を更新し、気づく経路は監査R1（経常費の欠落） |
| D20 | **分類器経路では、その親科目に紐づくうりぼーitemを全部0で初期化してから積む**（TKCに出てこなかった細目は0にする） | TKCが一次発生源なので「TKCに無い＝その月は発生していない＝0」が正しい。旧値を残すと分類先が変わったとき二重計上になる。計上が翌月にずれた場合は監査R1が警告する |
| D21 | **TKC仕訳自体が間違っている月は `--skip <科目コード>` で取込から外し、うりぼー側の正しい値を守る**（同時に税理士へ仕訳修正を依頼する） | 誤った仕訳をうりぼーに持ち込まない。画面のチェックボックス相当の逃げ道をCLIにも用意する |

## Consequences（この決定で何が変わるか・トレードオフ）

- 良くなること: 2026年度4〜7月で `rent` 121,000／`shopping_street` 11,800 が全月そろい、4月・5月の二重計上（各11,800円）が解消。4月は守口の hpb 69,914・microsoft・spotify・amazon_prime・garbage が未計上だったのが埋まり、6113の hpb/advertising 分類も実態（リクルート＝hpb、リジョブ＝advertising）に一致した。
- 引き受けるコスト・制約: D20 により「TKCに無い月は0」になるため、**計上が翌月にずれた費用は一旦0になる**（監査R1の警告で気づく前提）。D19 は金額一致判定なので、商店街費の額が変わると分離できずに rent へ吸われる（同じくR1で検知）。D21 は使うたびにTKC側の仕訳が直っていない証拠なので、skipが常態化しないよう修正依頼とセットで運用する。
- 積み残し: 2026/05 の寝屋川 `hpb` 132,000 は手入力の月額固定値で、実際にはリクルートへの5月支払いが無い（facts F14）。TKCに entry が無い月は D20 の0初期化も効かない（entry自体が生成されないため）ので、消すなら手作業。
